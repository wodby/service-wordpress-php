# WordPress on Wodby

What Wodby sets up for a WordPress application on this service, in addition to the PHP service it is based on. Check it before adding database, URL, salt or Redis settings to `wp-config.php`.

## What Wodby generates

On every start the container writes two files outside the codebase, from its environment variables:

- `$CONF_DIR/wodby.wp-config.php` (normally `/var/www/conf/wodby.wp-config.php`): the Wodby configuration.
- `$CONF_DIR/wp-config.php`: a complete `wp-config.php` that includes the file above and then `wp-settings.php`.

The generic `wodby.settings.php` of the PHP service is removed in this image; WordPress uses `wodby.wp-config.php` instead. Never edit the generated files or copy their values into the repository. They hold passwords: quote constant names, not values.

The WordPress root is the repository root, or the subdirectory named by the `docroot` setting of this service (variable `DOCROOT_SUBDIR`, `web` by default).

## Init action

On container start the service runs its init action (`WODBY2_SERVICE_INIT_ACTION`, here `init-wordpress`) against the WordPress root:

- With no `wp-config.php` there, it creates one that includes `wodby.wp-config.php` and then `wp-settings.php`.
- With an existing `wp-config.php` that does not mention `wodby.wp-config.php`, it inserts the include, marked `// Generated by Wodby`, just before the line that loads `wp-settings.php`. Keep that include.
- It makes `wp-content` and, when present, `plugins`, `themes`, `upgrade`, `languages`, `cache`, `wp-rocket-config` and `wflogs` under it writable by the web user.
- It replaces `wp-content/uploads` with a link to the files volume. This fails when the directory in the codebase holds anything other than a `.gitignore`: keep uploads out of the repository.

## What it configures

| Area | Constants | From |
| --- | --- | --- |
| Site URL | `WP_HOME`, `WP_SITEURL` | `WODBY_PRIMARY_URL` |
| Database | `DB_HOST`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_CHARSET`, `DB_COLLATE` | `DB_*` of the linked database, `DB_CHARSET`, `DB_COLLATION` |
| Keys and salts | `AUTH_KEY`, `SECURE_AUTH_KEY`, `LOGGED_IN_KEY`, `NONCE_KEY` and the matching `*_SALT` | `WP_AUTH_KEY` … `WP_NONCE_SALT`, generated by Wodby |
| Table prefix | `$table_prefix` | `WP_TABLE_PREFIX` |
| Debug | `WP_DEBUG` | `WP_DEBUG` |
| File system | `FS_METHOD` set to `direct` | — |
| Redis or Valkey | `WP_REDIS_HOST`, `WP_REDIS_PORT`, `WP_REDIS_PASSWORD`, `WP_REDIS_DATABASE`, `WP_REDIS_PREFIX` | `REDIS_HOST`, `REDIS_PORT`, `REDIS_PASSWORD`, `REDIS_DATABASE`, `REDIS_PREFIX` |

Every constant is defined only when it is not defined yet, and `$table_prefix` only when it is not set. A value the project defines above the Wodby include therefore wins; do not define these constants there unless an override is intended.

The file also sets `$_SERVER['HTTPS']` from the `X-Forwarded-Proto` header and `$_SERVER['REMOTE_ADDR']` from `X-Real-IP`, so no proxy handling is needed in `wp-config.php`.

## Redis or Valkey object cache

A linked Redis or Valkey service sets `REDIS_HOST`, `REDIS_PORT` and `REDIS_PASSWORD` on this service. The `WP_REDIS_*` constants are defined only while `REDIS_HOST` is not empty. Wodby defines the connection constants and nothing else: an object cache plugin that reads `WP_REDIS_*`, and enabling its object cache drop-in, are the project's part.

## Files

- The volume is mounted at `$FILES_DIR` (`/mnt/files`) and shared with the web server. `wp-content/uploads` points to `$FILES_DIR/public`.
- Only uploads are on the volume. Plugins, themes and other files written under `wp-content` from the WordPress admin land in the container's file system and are replaced by the next build or restart; add them through the repository.

## Tools and scheduled work

- WP-CLI is available as `wp`.
- The service declares one cron job that runs `wp cron event run --due-now`.

## Changing configuration

Set environment variables on this service (`WP_DEBUG`, `WP_TABLE_PREFIX`, `REDIS_DATABASE`, `REDIS_PREFIX`, `DB_CHARSET`, `DB_COLLATION`, and the `PHP_*` variables of the PHP service), or change the `docroot` setting. The generated files pick the values up when the container starts after the next deployment.

This service has no development workspace.

## Check the result

- `wp eval 'echo DB_HOST, PHP_EOL, WP_HOME, PHP_EOL;' --path=<WordPress root>` shows values that came through the generated file.
- `wp eval 'var_dump(defined("WP_REDIS_HOST"));' --path=<WordPress root>` tells whether the Redis constants are defined.
- `wp db check --path=<WordPress root>` confirms the database connection.
